# 導入手順書

Next.js(App Router) + Firebase + LINE Messaging API / LIFF で構築する、
友だち追加の流入経路計測 & 購入成果計測ツールです。

**動作環境**: Next.js 16(React 19)、Node.js 24.x(`package.json`の`engines`で指定。Vercelの「Node.js Version」も24.xにそろえる。Node.js 20.xはVercelでサポート終了)。管理画面のログイン判定(旧ミドルウェア)は、Next.js 16の名称に合わせて`src/proxy.ts`にしている。Excelファイルの読み込みは行わず、取り込みはCSVのみ。依存パッケージの脆弱性は、更新のたびに`npm audit --omit=dev`で確認する。

## セットアップ

```bash
npm install
cp .env.local.example .env.local  # 値を埋める
npm run dev
```

## 事前準備

1. **LINE Developersコンソール**
   - Messaging APIチャネルを作成し、`LINE_CHANNEL_ACCESS_TOKEN` / `LINE_CHANNEL_SECRET` を取得
   - Webhook URLに `https://<デプロイ先>/api/line/webhook` を設定し、Webhookを有効化
   - LIFFアプリを1つ作成し(エンドポイントURL: `https://<デプロイ先>/liff/add`)、`NEXT_PUBLIC_LIFF_ID` に設定
   - LIFFのスコープは `openid` のみでよい(`profile`は使用しておらず、有効にすると初回アクセス時に権限許可画面が挟まり遅くなるだけなので不要)
   - **Lステップの流入経路リンクを併用する場合**は、このLIFFの「スコープ」と「友だち追加オプション(Bot link feature)」を、Lステップ側が使っているLIFFアプリの設定とまったく同じにする。設定が違うと、本ツールのLIFFとLステップのLIFFで、友だち追加前にLINEの同意画面が2回出る(同じにすると1回で済むことを実機で確認済み)
   - 公式アカウントの「友だち追加URL」(`https://line.me/R/ti/p/@`から始まるもの)を`LINE_OFFICIAL_ACCOUNT_URL`に設定

2. **Firebase**
   - プロジェクトを作成し、Firestore・Storageを有効化
   - サービスアカウントキーを発行し、`FB_PROJECT_ID` / `FB_CLIENT_EMAIL` / `FB_PRIVATE_KEY` に設定
   - ブラウザ用のWeb SDK(`NEXT_PUBLIC_FIREBASE_*`)は使っていない(データの読み書きはすべてサーバー側のサービスアカウントで行うため、設定不要)

3. **管理画面ログイン**
   - `ADMIN_SESSION_SECRET` に、十分に長いランダムな文字列を設定(例: `openssl rand -hex 32` の出力をそのまま使う)
   - 最初の1人目(管理者権限)のアカウントを、以下のコマンドで作成する(2人目以降は `/admin/users` 画面から作成できる)
     ```bash
     node scripts/create-admin-user.js <ログインID> <パスワード> [表示名]
     ```

## 主な仕組み

### 流入経路名の構成要素

`/admin/sources`(流入経路管理)で流入経路を登録する際、名前は1つの自由入力欄ではなく、以下の要素に分けて入力する(すべて任意項目だが、少なくとも1つは入力する必要がある)。

- 設置先
- 訴求
- ポップアップ
- シナリオ
- 離脱地点
- 中間ページ
- その他(上記に当てはまらない要素)

一覧・他画面(クリックログ・成果ログ・日次レポート等)に表示される「名前」は、入力した要素を「_」区切りで結合して自動生成される(例: `LP上部_夏セール訴求_ポップアップA_シナリオ1_離脱ポイントA_中間ページ2`)。空欄の要素は結合時にスキップされる。

**一括登録**: `/admin/sources`の上部の「流入経路の一括登録(CSV)」ボタン(普段は閉じており、押すとパネルが開く。入力途中の状態は閉じても保持される)から、CSVで複数の流入経路をまとめて登録できる(`/api/sources/bulk`)。列は左から「設置先、訴求、ポップアップ、シナリオ、離脱地点、中間ページ、その他、Lステップ流入経路リンク」の順。1行目の見出し行は、あっても無くてもよい(A1が「設置先」または旧名称の「設置場所」なら見出しとして読み飛ばす)。名前は上記と同じ規則で自動生成し、すでに登録済みの名前・ファイル内で重複する名前、全項目が空の行、Lステップのリンクが`http`で始まらない行はスキップする。1回の取り込みは1,000行まで(書き込みは新規の件数分、400件ずつのバッチ)。実行前に「新規登録／スキップ」の件数を確認できる。

各要素はFirestore上でも個別のフィールド(`placement`/`appeal`/`popup`/`scenario`/`exitPoint`/`intermediatePage`/`other`)として保存されるため、将来的に要素ごとの集計・絞り込みにも利用できる(実際に「ポップアップ」「シナリオ」「離脱地点」は下記の日次レポート(◯◯別)の集計軸として使われている)。「通数」は流入経路には無く、広告側の項目(下記)であることに注意。

### 広告名の構成要素

`/admin/purchase-links`(広告管理)で広告を登録する際も、流入経路名と同じ考え方で、名前を以下の要素に分けて入力する(すべて任意項目だが、少なくとも1つは入力する必要がある)。

- シナリオ(数値を入力すると「1st」「2nd」「3rd」...のように自動で序数表記になる)
- 通数(数値を入力すると「◯通目」の表記になる。レポート集計での突き合わせ用)
- その他(上記に当てはまらない要素)

表示名は「_」区切りで自動生成される(例: `1st_500通目`)。Firestore上は`scenario`(序数表記済みの文字列)/`messageCount`(数値)/`other`の個別フィールドとして保存される。既存データ(この項目が追加される前に登録した広告、または「1st」等の形式に一致しないシナリオ値を持つデータ)は、`/admin/purchase-links`の「編集」を開くと、既存の値がそのまま「その他」欄に引き継がれた状態で表示される(流入経路と同様、自動での振り分けは行わない)。

**既存データについて**: この機能が追加される前(2026年9月25日より前)に登録した流入経路は、これらの構成要素を持たず、結合済みの`name`のみの状態になっている。無理に自動分割はしないため、`/admin/sources`の一覧で「編集」を開くと、既存の名前がそのまま「その他」欄に引き継がれた状態で表示される。必要に応じて、その内容を適切な要素欄に手動で振り分け直すことができる。

### 友だち追加の流入経路計測
1. 流入経路ごとに `/liff/add?mode=add_friend&sourceId=xxx` のリンクを発行して広告・SNS等に設置
2. リンクを開くとLIFFが起動し、`userId` を取得した上でクリックログ(`clicks`)に記録
3. その後、リダイレクト先(下記参照)へ遷移
4. ユーザーが実際に追加すると `follow` Webhookが届き、直前のクリックログと`userId`で突き合わせて `friends` に `sourceId` を記録

**導入前から友だちだった人の自動登録**

ツール導入前から公式アカウントの友だちだった人は、友だち追加の通知(follow)がツールに届かないため、そのままでは友だち一覧に載らない。そこで、友だち追加リンク(流入経路リンク)のクリック時(`/api/track/click`)に、友だち一覧に未登録のユーザーについてLINEのプロフィール取得(Messaging API。友だち・ブロックしていない人にしか成功せず、友だちでなければ404)を行い、成功した場合は「導入前からの友だち」として自動登録する(`src/lib/register-existing-friend.ts`)。

- 登録内容: 表示名・アイコン・ID(通常の友だち追加と同じ連番。追加日時の順にはならない)・流入経路(そのとき踏んだリンクのもの。本当の最初の流入経路とは限らない)。`preExisting: true`(友だち一覧の「導入前」列)と`addedAtEstimated: true`(追加日時が仮)が付く。追加日時は「リンクを踏んだ日時」で代用する
- 友だちでない人(未追加・ブロック中)は取得が404になるため、従来どおり「未追加」として扱い、友だち追加の通知を待つ
- 流入経路ログの「状態」には「既存の友だち(自動登録)」(`statusAtClick: "registered"`)と記録する。取得・登録に失敗した場合もクリックの記録は続け、`track_click.register_existing_friend_failed`としてエラー・システムログに記録する(次のクリックで再度試みる)
- **追加日時が仮の間(`addedAtEstimated`)は、日ごとの集計(`daily_stats`)・レポートの友だち追加数に含めない**(リンクを踏んだ日の友だち追加数が増えて見えるのを防ぐため)。追加日時が確定した時点で、その日付の友だち追加数に加算される
- 友だち追加の直後にクリックの記録が遅れて届いた場合に、新規の友だちが誤って「導入前」として登録される競合に備え、自動登録から2分以内にfollowの通知が届いた場合は「導入前」の印を外す。導入前の友だちがブロック→再追加した場合は、その時点の日時で新規の追加として数える(印は残る)
- 広告リンク(購入導線)のクリックでは自動登録しない(流入経路が決まらないため)

**「友だち追加時の流入経路」「最新の流入経路」の固定表示について**

「広告クリックログ」の「友だち追加時の流入経路」「最新の流入経路」と、「流入経路ログ」の「友だち追加時の流入経路」は(流入経路ログには「最新の流入経路」の列は表示しない)、クリックが記録された**その時点の値をそのまま保存(スナップショット)**しており、後からその友だちが別の流入経路リンクをクリックして「最新の流入経路」が変わっても、過去のクリックログの表示は変わらない。成果ログの「最新の流入経路」も同様に、成果発生時点の値で固定される。

- 流入経路ログでは、スナップショットが無い古い記録は現在の値で補完せず、「友だち追加時の流入経路」を「(記録なし)」と表示する。クリックした流入経路の名前も記録時点のものを`clicks.sourceNameAtClick`に保存して固定する(古い記録のみ現在の名前を使う)
- 流入経路ログの「状態」もクリック時点で固定する(`clicks.statusAtClick`: `unidentified`=未特定 / `not_added`=未追加 / `existing`=既存の友だち(再クリック) / `unblocked`=ブロック解除(`unfollowedAt`がある友だちがリンクを押した) / `registered`=既存の友だち(自動登録。導入前から友だちだった人が初めてリンクを押した))。以前の「新規追加」(後から友だち追加が完了したか)は表示しない。古い記録は「(記録なし)」
- 友だちがまだ未登録の状態で最初に押された友だち追加リンクのクリックは、そのクリックの流入経路を「友だち追加時の流入経路」として記録する
- 保存先はクリックログ自体(`clicks`コレクションの`friendSourceIdAtClick`・`friendLatestSourceIdAtClick`)
- この項目が追加される前(2026年9月25日より前)に記録された古いクリックにはこのスナップショットが無いため、その場合のみ友だちドキュメントの現在の値を表示する(その古い行だけは今の値が表示される)

**リダイレクト先について**

`/admin/sources` の各流入経路に「Lステップの流入経路リンク」を設定できる。

- 設定した場合:このツールでのクリック記録後、指定したLステップの流入経路リンクへリダイレクトする(Lステップ側でも同じ流入経路の計測を行いたい場合に使用。このツールの流入経路Aにはaのリンク、Bにはbのリンク、というように1対1で紐付けられる)
- 未設定の場合:`.env.local` の `LINE_OFFICIAL_ACCOUNT_URL`(通常の公式アカウント友だち追加URL)へリダイレクトする

### 広告の成果計測

LINEのLIFFという仕組みは、「`https://liff.line.me/{LIFF ID}` という専用URL経由で開かれた場合」にだけ、そのページにログイン状態などの情報を渡してくれる。逆にいうと、一度自社サーバーを経由してリダイレクトしてしまうと、ページ側でLIFFのSDKを呼んでも正しくユーザーを識別できない(この制約はLINE側の仕様であり、回避できない)。

そのため、次の方式を採る。**購入ページ(LP)そのものを、LIFFアプリの「エンドポイントURL」として登録する。** これにより自社サーバーを一切経由せず、LINEが直接LPを開いてくれるため、表示は速く、かつLIFF側も正しくログイン状態を認識できる。

1. **LP側の事前準備(初回・LPごとに1回だけ)**
   - LINE Developersコンソールで、そのLPのURLを「エンドポイントURL」としたLIFFアプリを作成する(LINEログインチャネル配下、スコープは `profile` と `openid` を有効化)
   - 発行されたLIFF IDを控えておく

2. **`/admin/purchase-links` で広告を登録**する際に、名前・遷移先URL(上記でエンドポイントURLに設定したLPのURL)・そのLIFF IDを入力する。計測リンクとして `https://liff.line.me/{LIFF ID}?purchaseLinkId=xxx` が発行される

3. 購入ページ・サンクスページ(決済完了後のページ)にそれぞれ以下のタグを設置する

   ```html
   <!-- 購入ページ(LP) -->
   <script src="https://<デプロイ先>/track.js" data-liff-id="そのLPに対応するLIFF ID"></script>

   <!-- サンクスページ(決済完了ページ)。LIFFの設置は不要 -->
   <script src="https://<デプロイ先>/track.js" data-conversion="true"></script>
   ```

4. リンクをクリックすると、LINEが直接LPを開く。`track.js` はページの表示を一切ブロックせず、裏側でLINEのログイン状態を確認し、識別できた場合はクリック記録(`clicks`)に`userId`を含めて記録する。識別できなかった場合(外部ブラウザで開かれた等)でも記録自体は行われ、「未特定」として扱われる
5. サンクスページでは `track.js` が保存しておいた`clickId`を使って `/api/track/conversion` を呼び、`conversions`へ記録する
6. 購入ページとサンクスページが同一ドメインである必要がある(clickIdの引き継ぎにlocalStorage/Cookieを使うため)。決済代行サービス等の別ドメインを挟む場合は、URLのクエリパラメータで`clickId`を引き継ぐ形に変更が必要

※ `/liff/add?mode=purchase&purchaseLinkId=xxx` という旧方式のリンクも後方互換のため残っているが、中間ページを経由する分だけ遷移が遅く、新規に発行するリンクは必ず `/admin/purchase-links` から取得すること。

### 友だち一覧の「ID」「Lステップナンバー」

「友だち一覧」画面(`/admin`)の表示名の左に、以下2種類の番号を表示する。右端の「導入前」列には、導入前から友だちだった人(自動登録)に「導入前」(追加日時が未確定のうちは「導入前(日時未確定)」)と表示する。絞り込み「導入前の友だち」(導入前／通常)でも探せる。

- **ID**: 友だち追加日時が古い順の連番。新規に友だち追加された友だちには、LINE Webhook側(`handleFollow`)でトランザクションにより自動で採番される(`counters/friendIdNumber`ドキュメントの値をインクリメントして採番するため、同時に複数人が追加されても重複しない)。この機能を追加する前から登録されていた既存の友だちへの一括付与は、導入時に一度だけ行えばよい作業のため、恒常的な画面機能としては用意していない(必要であれば、`addedAt`昇順で1から連番を振るスクリプト・APIを都度用意して実行する)
- **Lステップナンバー**: Lステップ側の管理番号。画面上部の「友だち情報の一括更新」で、CSVから付与・修正できる(下記)

#### 流入経路・追加日時の手動変更

友だち一覧の各行の右端にある鉛筆アイコンから、その友だちの「友だち追加時の流入経路」を手動で変更できる(`PUT /api/admin/friends/[userId]`。管理者権限のみ)。「導入前」の友だちは「友だち追加日時」も変更できる(通常の友だちの追加日時は、友だち追加時に記録された正しい値のため変更できない)。

- 流入経路は、流入経路管理に登録済みのもの、または「直接追加」から選ぶ。「流入経路名で検索」欄に文字を入れると、その文字を含む流入経路だけが一覧に出る(大文字小文字・全角半角は区別しない。1件に絞られた状態でEnterを押すとそれを選ぶ。一覧は枠の中でスクロールできる)。現在選んでいるものは「選択中」に表示される
- 導入前の友だちは、日時を指定して保存すると追加日時が確定した扱いになる(「導入前(日時未確定)」から「導入前」へ。その日の友だち追加数に加わる)。確定後も何度でも修正できる
- 日ごとの集計(レポートの友だち追加数)も付け替える。過去のクリックログに記録された流入経路は変わらない(クリック時点の記録として固定のため)
- 未来の日時は指定できない

#### 友だち情報の一括更新(CSV)

友だち一覧の上部の「友だち情報の一括更新(CSV)」で、友だちの情報をまとめて更新する(`POST /api/admin/friends/bulk-update`。管理者権限のみ)。友だち一覧が見えにくくならないよう、普段は閉じており、ボタンで開閉する(閉じても入力途中の状態は保持される)。

ファイルの見出し行は **「ID」「表示名」「友だち追加日時」「流入経路名」「Lステップナンバー」**。「ID」は必須で、友だち一覧の「ID」の番号で友だちを1対1に特定する(表示名・日時での突合はしない)。残りの列は、**ファイルに列があり、かつセルに値がある項目だけ**を更新する(空欄は変更しない)。友だち一覧のCSV出力(ID・表示名・Lステップナンバー・流入経路・友だち追加日時を含む)を編集して、そのまま取り込み直すこともできる。「流入経路」「登録経路」「追加日時」などの見出しも読み取る。

- **友だち追加日時**: 「導入前」の友だちのみ更新する。更新すると「日時が仮」の状態が解除され、その日の友だち追加数に加わる。確定後も何度でも修正できる。通常の友だち(友だち追加の通知で登録された人)は正しい値が記録されているため変更せず、「導入前ではないため変更なし」として件数に出す。未来の日時も更新しない
- **流入経路名**: このツールの流入経路管理に登録済みの名前、または「直接追加」と完全一致する場合のみ更新する(一致しない場合は変更せず、件数と名前の例を出す)。導入前・通常のどちらの友だちも対象。過去のクリックログの流入経路は変わらない(クリック時点の記録のため)
- **Lステップナンバー**: すべての友だちが対象
- **表示名**: 更新はしない。IDの取り違えに気づけるよう、ファイルの表示名が友だちの表示名と異なる件数を出すためだけに使う
- 日ごとの集計(レポートの友だち追加数)も、追加日時・流入経路の変更に合わせて付け替える。日時が未確定の友だちの流入経路だけを更新した場合は、集計には入れない(日時の確定時に加算される)
- ファイルを選ぶと、実行前に「IDが一致した人数」「更新される件数」「IDが見つからない行」などを確認できる。IDを読み取れない行・日時を読み取れない行は対象外として件数に出す。同じIDが複数行ある場合は最後の行を使う
- **上限**: ファイルの行数は20,000行まで。IDは30件ずつ検索し、該当した友だちの分だけを読み込む。書き込みは400件ずつ。Vercel上の最大実行時間は60秒
- 友だち一覧の絞り込み「Lステップナンバー」で「未付与」を選ぶと、番号が付いていない友だちだけを表示できる。この更新ではIDは振り直さない

### レポートの読み込みを軽くする仕組み(日ごとの集計・キャッシュ)

レポート系の画面(日次・月次・ポップアップ別・離脱地点別・訴求別・シナリオ別・サマリ)は、期間内の友だち・成果のドキュメントを1件ずつ読み込むと、友だち数に比例してFirestoreの読み取りが増える。そのため次の仕組みで読み取りを抑えている。

- **日ごとの集計(`daily_stats`)**: 友だち追加・成果が発生するたびに、その日(日本時間)の集計ドキュメント(`daily_stats/YYYY-MM-DD`)へ件数を加算する(流入経路ID別・成果は流入経路ID×広告ID別。手動追加の成果は広告名別)。レポートはこの集計ドキュメント(1日につき1件)だけを読むため、1年分でも読み取りは約365件。流入経路・広告の名前やポップアップ名・成果単価などは、読み出し時に最新の設定から引く(編集すると過去分のレポートにも反映される)。
  - 加算するタイミング: 友だち追加(LINE Webhookのfollow。ブロック後の再追加は付け替え)、友だち追加時の流入経路の補完(`direct`から実際の流入経路へ)、成果の自動計測、編集用成果ログでの非表示/表示に戻す、成果のCSV追加。
  - 集計の更新に失敗しても本来の処理は止めず、エラー・システムログ(`daily_stats.update_failed`)に記録する。
  - `daily_stats_meta/state.coverageFrom` 以降の日付だけ集計から読む。それより前の日付は、従来どおり元のドキュメントを直接読み込む。
  - **集計の開始は自動**: 最初の友だち追加・成果が記録されたとき(`daily_stats_meta/state`がまだ無いとき)に、自動で`coverageFrom`(記録した日の翌日)を設定する。ボタン等の操作は不要。それ以前の日付は元のドキュメントを直接読むため、すでにデータがある環境でもそのまま使える(記録した日の翌日から集計を読み始める)。
  - **集計がずれたとき(レポートの件数が友だち一覧・各ログと合わない)**: Firebaseコンソールで`daily_stats_meta`の`state`ドキュメントを削除する。次の友だち追加・成果の記録の翌日から集計を読み直し、それ以前は元のデータを直接読む(正しい件数に戻る)。`scripts/seed-test-data.js`・`scripts/delete-all-logs.js`は、実行時に集計(`daily_stats`・`daily_stats_meta`)を消去する。
- **レポート結果の短時間キャッシュ**(`src/lib/report-cache.ts`): 同じ期間のレポートはサーバーのメモリに2分間保持する。imp数・CL数・PV数の取り込みや編集、成果の追加/非表示、流入経路・広告の登録/編集では即時に破棄する。友だち追加・成果の自動計測では破棄しないため、新しい友だち追加・成果がレポートに反映されるのは最長2分後(サーバーが複数台の環境では、台ごとに保持するため同様に最長2分)。
- **「現在稼働中」の判定**(直近7日間の友だち追加・成果に登場するポップアップ等): 日ごとの集計から読むため、7日分の集計ドキュメントを読むだけで済む。レポートのキャッシュにも含まれる。

### 友だち一覧・ログ画面のページネーション

友だち一覧と各ログ(広告クリックログ・流入経路ログ・広告成果ログ・編集用成果ログ・エラー・システムログ)は、50件ずつ表示するページネーション(「前の50件」「次の50件」と、「現在のページ / 全ページ数」の表示)。全ページ数は表示しない(数えるために読み取りが増えるため。「N ページ目」のみ表示)。全件を一度に読み込まず、次のページを開いたときに続きの50件だけを取得する(`/api/admin/table`、実装は`src/lib/log-tables.ts`)。

- **ログのデフォルトは当日分のみ**: ログ画面を開いた直後は、日時の絞り込みが「当日(日本時間)」に設定されている。過去分は日時の開始・終了を変えるか、「全期間を表示」を押す。友だち一覧は日時の絞り込みなし(全期間)。
- **日時は日本時間**: 表示・絞り込みとも日本時間で扱う(サーバーの時刻設定に依存しない)。
- **絞り込みはサーバー側**: 絞り込み条件はすべて全件が対象。ユーザー名・流入経路などの条件に合う行が少ない場合は、1回の操作で最大1,000件まで読み込んで探し、見つからなければ「次の50件」で続きを探す。
- **CSV・スプレッドシート出力**: 現在の絞り込み条件に合う全件が対象(最大10,000件。超える場合は期間などで絞り込む)。
- 流入経路管理・広告管理も、50件ずつ表示するページネーション(登録件数が少ないうちは1ページのみ)。
- 編集用成果ログは、自動計測の成果(`conversions`)と手動追加の成果(`report_cv_entries`のkind=import)を成果日時の新しい順に1本にまとめて読み込む(`cv_log`)。非表示のものも一覧に含め、状態の列で見分ける

### ログ画面のCSVダウンロード・スプレッドシートへの出力

広告クリックログ・流入経路ログ・成果ログ・友だち一覧・エラー/システムログの各画面には、その時点で絞り込んだ内容(何も絞り込んでいなければ全件)を出力するボタンを用意している。

- **CSVダウンロード**: ブラウザだけで完結し、追加設定は不要
- **スプレッドシートに送信**: ログイン必須(`/api/logs/export-to-sheet`も`proxy.ts`の対象)で、管理者権限のみ(レポート閲覧権限ではボタンを表示せず、サーバー側でも拒否する。CSVダウンロードは閲覧権限でも可)。Googleスプレッドシートへの書き込みには認証が必要なため、あらかじめ「Google Apps Script(GAS)のWebアプリ」を1つ用意し、そのURLを`SHEETS_EXPORT_WEBHOOK_URL`に設定しておく必要がある(Lステップへの転送で使っている`LSTEP_WEBHOOK_URL`と同じ考え方)。この1つのWebアプリURLに対して、送信先のスプレッドシート・シート名・書き込み方法を画面側から指定できる

**「スプレッドシートに送信」ボタンで指定できる内容**

ボタンを押すと設定欄が開き、送信のたびに以下を指定できる(直前に使った内容はブラウザに保存され、次回開いた際に初期値として復元される)。

- **スプレッドシート**: 書き込み先のスプレッドシートのURLまたはID。空欄の場合は、GASスクリプトがバインドされているスプレッドシート(後述の手順1で開いたもの)がそのまま使われる
- **シート名**: 書き込み先のシート(タブ)名。空欄の場合は画面ごとに決まっている既定名(`purchase_clicks`/`source_link_clicks`/`conversions`/`events`/`friends`等)が使われ、そのシートが存在しなければ自動で新規作成される
- **書き込み方法**:
  - 「末尾の空白行に追加」: シートの一番下の行の続きに追記する(見出し行が無ければ先頭に追加する)。従来からの既定動作
  - 「シートを上書き」: シートの既存の内容をすべて消去してから、見出し行・データ行を先頭(A1)から書き込み直す
  - 「指定したセルから書き込む」: 指定した左上セル(例: `B3`)を起点に、見出し行・データ行を書き込む。それ以外の既存セルの内容には触れない

**GAS側の設定手順**

1. 書き込み先にしたいGoogleスプレッドシートを開き、「拡張機能」→「Apps Script」を開く
2. 以下のコードを貼り付ける

   ```javascript
   function doPost(e) {
     try {
       var body = JSON.parse(e.postData.contents);
       var logType = body.logType; // "friends" / "purchase_clicks" / "source_link_clicks" / "conversions" / "event_logs"
       var headers = body.headers; // 列見出しの配列
       var rows = body.rows; // 行データの配列(各行は文字列の配列)
       var writeMode = body.writeMode || "append"; // "append" / "overwrite" / "cell"
       var startCell = body.startCell; // writeMode === "cell" の場合のみ、例: "B3"
   
       // spreadsheetIdの指定があればそのスプレッドシートを開く。無ければこのスクリプトが
       // バインドされているスプレッドシート(コンテナバインド)をそのまま使う。
       var ss = body.spreadsheetId ? SpreadsheetApp.openById(body.spreadsheetId) : SpreadsheetApp.getActiveSpreadsheet();
       var sheetName = body.sheetName || logType;
       var sheet = ss.getSheetByName(sheetName) || ss.insertSheet(sheetName);
   
       if (writeMode === "overwrite") {
         sheet.clearContents();
         sheet.getRange(1, 1, 1, headers.length).setValues([headers]);
         if (rows.length > 0) {
           sheet.getRange(2, 1, rows.length, headers.length).setValues(rows);
         }
       } else if (writeMode === "cell") {
         var startRange = sheet.getRange(startCell);
         var startRow = startRange.getRow();
         var startCol = startRange.getColumn();
         sheet.getRange(startRow, startCol, 1, headers.length).setValues([headers]);
         if (rows.length > 0) {
           sheet.getRange(startRow + 1, startCol, rows.length, headers.length).setValues(rows);
         }
       } else {
         // append: シートが空の場合だけ見出し行を書き込み、その後ろにデータ行を追記する
         if (sheet.getLastRow() === 0) {
           sheet.appendRow(headers);
         }
         if (rows.length > 0) {
           sheet.getRange(sheet.getLastRow() + 1, 1, rows.length, headers.length).setValues(rows);
         }
       }
   
       return ContentService.createTextOutput(JSON.stringify({ ok: true })).setMimeType(
         ContentService.MimeType.JSON
       );
     } catch (err) {
       // 失敗した場合は、ツール側にエラー内容を返す
       return ContentService.createTextOutput(JSON.stringify({ ok: false, error: String(err) })).setMimeType(
         ContentService.MimeType.JSON
       );
     }
   }
   ```

3. 「デプロイ」→「新しいデプロイ」→種類は「ウェブアプリ」を選択
   - 実行するユーザー: 自分
   - アクセスできるユーザー: 全員
4. デプロイ後に発行される「ウェブアプリのURL」を`.env.local`の`SHEETS_EXPORT_WEBHOOK_URL`に設定する

※ `spreadsheetId`が指定された場合、GASの実行者アカウントがそのスプレッドシートに編集権限を持っている必要がある(手順3で選んだ「実行するユーザー」のGoogleアカウントに、書き込み先スプレッドシートの編集者としてのアクセス権を付与しておくこと)。

### エラー・システムログ

友だち追加・流入経路リンクのクリック・成果計測の各過程で、「通常と異なること(警告・エラー)」が起きた場合に記録する仕組み。何かトラブルが起きた際に、原因を`/admin/logs/events`(「エラー・システムログ」)画面から追跡できるようにするためのもの。

- **記録先**: Firestoreの`event_logs`コレクション
- **記録される内容**: `level`(info/warn/error)、`stage`(どの処理で起きたか)、`message`(日本語の説明)、`context`(userId・sourceId・clickId・エラー詳細等)
- **記録されるタイミングの例**
  - LINE Webhookの署名検証失敗、Lステップへの転送失敗
  - 友だち追加時、流入経路リンクのクリック記録が見つからない(直接追加として扱われた)場合
  - LINEプロフィール取得の失敗
  - クリック記録APIの呼び出し時にIDトークンの検証に失敗した場合・IDトークン自体が届かなかった場合
  - 成果計測時に、対応する広告のクリック記録が見つからない場合
  - `/liff/add`(友だち追加リンク)ページでのLIFF初期化・ログイン処理の失敗、Lステップ流入経路リンクの取得失敗
  - `track.js`(購入LP・サンクスページに設置するスクリプト)内でのLIFF SDK読み込み失敗・初期化失敗・API送信失敗

**あえて記録していないもの**: 正常に完了した友だち追加・クリック・成果は、それぞれ`friends`・`clicks`・`conversions`コレクション自体に記録が残るため、`event_logs`には記録しない。これにより、ログ画面を「普段は空、何かあった時だけ表示される」状態に保ち、見やすさと書き込みコストの両方を確保している(想定されるアクセス数からしても、書き込み件数はごくわずかで、費用への影響は無視できる範囲)。

### 日次レポート・編集用成果ログ

「日次レポート」画面(`/admin/reports/daily`)は、指定した期間について日ごとの指標を一覧で確認できる画面。デフォルトは直近30日間で、期間は自由に変更できる。日付の列見出しをクリックすると昇順・降順を切り替えられる。

列は左から「PV数、imp数、imp率(imp数 ÷ PV数)、CL数、CL率(CL数 ÷ imp数)、友だち追加数、友だち追加率(友だち追加数 ÷ CL数)、CV数、CVR(CV数 ÷ 友だち追加数)」の順で、広告接触から友だち追加・購入までの流れをそのまま追える並びになっている。

月ごとの総計行(背景色を変えて区別している)を、各月のまとまりの先頭(画面の上側)に来るように挿入して表示する。具体的には、昇順(古い→新しい)表示ではその月の月末の行の直後に、降順(新しい→古い、既定の並び順)表示ではその月の月末の行の直前に挿入する(降順では月末の日付が先に表示されるため、結果的にどちらの並び順でも総計行はその月の一番上に来る)。日付の並び順はいつでも切り替えられ、切り替えるたびに総計行の位置もそれに追従する。この月次総計の判定・集計ロジックは`src/lib/monthly-totals.ts`の`buildMonthlyDisplayItems()`に共通化されており、下記のポップアップ別・シナリオ別・離脱地点別・訴求別の4レポート(それぞれのポップアップ・シナリオ等ごとのテーブル単位)でも同様に挿入される。

CV数は、自動計測された成果ログ(`conversions`)をそのまま使うのではなく、「編集用成果ログ」画面(`/admin/reports/cv-log`)で手を加えた結果を反映した件数になっている。

- **CSVでの手動追加**: 決済代行サービス側の管理画面など、このツールが自動計測できない経路で発生した成果を追加できる。列は「成果日時(YYYY/MM/DD または YYYY/MM/DD HH:mm)、メモ、流入経路名、広告名」の順(メモ以降は空欄可、見出し行があっても自動で無視される)。追加された成果には一覧上で「インポート」の印がつく。CSV(.csv)ファイルをそのままアップロードできる(Excelファイルは取り込めないため、CSVで保存し直す)
- **非表示(除外)**: 誤って記録された成果・二重計上等を、実際のログを消さずに日次レポートの集計対象から外せる。一覧の「非表示にする」ボタンからの個別操作、チェックボックスでの複数選択(ページをまたいで選択でき、一覧の上のボタンで一括して非表示/表示に戻す)、またはID列を使ったCSV一括操作(列は「ID」1列のみ。`POST /api/report/cv/visibility`に`{hidden, ids}`を渡す。成果の種類・日時はサーバー側でIDから調べるため、画面に表示していない期間の成果のIDも指定でき、見つからないIDは「一致せずスキップ」として件数に出す。1回5,000件まで)のいずれでも可能。非表示にした行は薄く表示され、状態の列が「非表示」になる。いつでも「表示に戻す」で戻せる
- これらの操作はすべて`report_cv_entries`という別コレクションに記録され、自動計測の記録(`conversions`)自体は書き換わらない
- **絞り込み**: 通常のログ画面と同様に、成果日時(期間。開いた時は当日、「全期間を表示」で解除)・友だち名・流入経路・広告・種別(インポート/自動計測)・状態(表示中/非表示)で絞り込める。成果日時の期間はサーバー側の範囲指定、その他は読み込んだ行からの絞り込み。流入経路のプルダウンには登録済みの流入経路と「直接追加」が並び、手動追加の成果に自由入力した流入経路名は、プルダウンには出ない(一覧には表示される)。CSVダウンロード・スプレッドシート送信も他のログ画面と同じ

**PV数・imp数・imp率・CL数について**: これらはこのツールが自動計測しているものではなく、Flipdesk等・PV数集計ツールの管理画面からエクスポートしたCSVファイルを、下記「データ取り込み」画面からインポートして表示する。

- **PV数のCSV取り込み**: 「データ取り込み」画面の「PV数」から行う。見出し行に「日付」「合計」の2列が必要で、「合計」列の値をその日のPV数として取り込む(列の判定ロジックは`src/lib/pv-import.ts`の`parsePvRows()`)。同じ日付を再度取り込んだ場合、値は合算されず最新の内容に置き換わる
- **手動での入力・修正**: PV数・imp数・CL数はいずれも、一覧の各行右端の「編集」ボタンから手動で入力・修正することもできる。値を空欄にして保存すると、その項目は「未入力」の状態(未インポート扱い、表示は「-」)に戻る
- **メモ欄**: 一覧の右端(請求額の右)に「メモ」列があり、日ごとにメモを書ける(2,000文字まで)。入力は「編集」を押したときのみで、PV数・imp数・CL数と一緒に保存する。レポート閲覧権限では表示のみで、編集は不可(APIも拒否)。メモ内のURLはリンクとして開ける(新しいタブ)。「表示名(URL)」と書くと表示名がリンク文字になり(全角の`（ ）`も可)、URLだけを書いた場合はURL自体がリンクになる。リンクにするのはhttp・httpsのみ(`src/lib/memo-links.ts`)。表示名は、かっこの直前の文字から前の空白・改行までなので、文章の途中に置く場合は表示名の前に空白か改行を入れる。メモはCSVにも出力される。保存先は下記の`daily_ad_metrics`の`memo`フィールドで、CSV取り込みでは消えない
- 「編集」ボタンは他のレポートと同じ鉛筆アイコンで、編集中は「保存」「取消」を縦に並べて表示する
- 保存先は`daily_ad_metrics`コレクション(ドキュメントID=日付, `YYYY-MM-DD`)。PV数・imp数・CL数はそれぞれ別のタイミングで入力・修正されることを想定し、更新時は該当するフィールドだけを上書きする(CSV取り込み・手動編集のどちらから更新した場合も同様)

### ポップアップ別日次レポート

「ポップアップ別」画面(`/admin/reports/daily-by-popup`)は、ポップアップごとに日ごとのPV数・imp数・CL数・CL率・友だち追加数・友だち追加率・CV数・CVRを一覧できる画面。デフォルトは直近30日間で、期間は自由に変更でき、日付見出しのクリックで昇順・降順を切り替えられる。チェックボックスで選んだポップアップの分だけ、1つのテーブルの中に列としてまとめて表示する(日付列は左端に固定されており、どのポップアップの列を見ていても同じ日付の行が横に揃って見える。縦スクロールも共通の1つの領域で行うため、個々のポップアップ内で別々にスクロールすることはない)。列が多くフォントも小さめにしているため、横方向は必要に応じてテーブル全体をスクロールして確認する。PV数の「編集」操作は、各行の鉛筆アイコンボタンから行う(`src/app/admin/icons.tsx`の`EditPencilIcon`)。隣り合うポップアップの境目には区切り線(`ui.compareGroupDividerBorder`)を引いて見分けやすくしている。チェックボックスの初期状態・テーブルの見出しでは、「現在稼働中」のポップアップ(直近7日間=`ACTIVE_WINDOW_DAYS`(`src/lib/report-cv.ts`)に友だち追加・成果・imp数/CL数の取り込みのいずれかがあったもの)だけを自動選択し、太字・バッジ(`ui.activeLabelText`・`ui.activeLabelBadge`)で強調する(`getActivePopupLabels()`等がAPIレスポンスの`activeLabels`として返し、表示期間の指定とは独立して常に直近の実データで判定する。稼働中が1つも無い場合は全件を選択する)。このレイアウト(`ui.compareTable`系のスタイル、`src/app/admin/ui.ts`)は、下記のシナリオ別・離脱地点別・訴求別日次レポート、でも共通して使っている(月次サマリは縦に名前を並べた別レイアウト)。

- 「ポップアップ」は、各流入経路(`/admin/sources`)に設定した「ポップアップ」構成要素をもとに集計する(流入経路名の構成要素は上記「流入経路名の構成要素」を参照)。imp数・CL数のインポートでしか登場しない(まだ友だち追加・成果の実績がない)ポップアップもテーブルとして表示される
- PV数はポップアップ単位では分かれていないため、このポップアップ専用の値(`daily_popup_ad_metrics`コレクションの`pvCount`)が未入力の場合は、通常の日次レポートに取り込んだ・入力したその日の合計PV数(`daily_ad_metrics`コレクションの`pvCount`)をそのまま表示にフォールバックする(訴求別レポートを除く)。このポップアップだけ別の値にしたい場合は、一覧の各行右端の「編集」ボタンから個別に入力・修正できる(更新は`/api/report/ad-metrics-by-popup/[date]`のPUT、body: `{ popup, pvCount }`)
- 成果の集計は、自動計測成果については「成果記録時点で最新だった流入経路」(`conversions.latestSourceId`。友だち追加後に別の流入経路リンクを再クリックしていた場合はそちらに更新されている)を優先し、再クリックが一度も無い場合は友だち追加時点(ファーストタッチ)の流入経路(`sourceId`)にフォールバックする。友だち追加数の集計は、追加というその場限りの出来事のため常に`sourceId`を使う
- ポップアップが未設定の流入経路(または該当する流入経路が見つからない場合)は「(未設定)」というテーブルにまとめる
- CSV等で手動追加した成果(`report_cv_entries`の`kind: "import"`。流入経路と紐付かない)は「(インポート)」という専用テーブルにまとめる
- CV数は通常の日次レポートと同様、「編集用成果ログ」画面で非表示にしたものを除いた実効件数
- 表示期間内に友だち追加・成果・imp数/CL数インポートのいずれかが1件でもあったポップアップについては、そのテーブルに期間内のすべての日付を行として含める(該当日が0件・未インポートでも行として表示する)
- テーブルの上に「表示するポップアップ」というチェックボックス一覧があり、ここで選んだポップアップのテーブルのみが表示される。期間を再取得するたびに、その時点で登場するポップアップはすべて選択状態にリセットされる(「すべて選択」「すべて解除」ボタンでまとめて切り替えも可能)
- 選択したテーブルは縦に並べず、横並び(左右にスクロール可能)で表示する。各テーブルは同じ幅で揃えてあり、列の位置がテーブル間でずれないようにしている
- CSVダウンロードは、チェックボックスの選択状態に関わらず、全ポップアップ分をポップアップ列付きの1つのCSVにまとめて出力する
- ここで表示されるポップアップ名は、「流入経路管理」で登録した「ポップアップ」要素の文字列と、imp数・CL数取り込み時に判定されたポップアップ名が完全一致する場合に同じテーブルへ統合される。表記ゆれ(全角半角・空白等)があると別のテーブルとして表示されるため、命名を揃えておくことを推奨

### 月次レポート(日次・月次の合算+月次サマリ)

日次5レポートとは別に、月単位で確認するための月次レポート(合算の月次、および月次サマリ)がある。いずれも**閲覧専用**(このレポート画面自体からPV数・imp数・CL数等を編集することはできない。修正したい場合は元になっている日次レポート側で行う)。期間は開始月・終了月を`<input type="month">`(ブラウザのプルダウン式の月選択UI)で指定する(既定値は直近6ヶ月)。実装は`src/lib/report-monthly.ts`に共通化している。

- **月次レポート(合算)**(日次レポートと同じページ`/admin/reports/daily`内の「日次/月次」ラジオボタンで切り替える。画面は`src/app/admin/reports/daily/page.tsx`が、日次=`DailyReportView.tsx`・月次=`MonthlyReportView.tsx`を切り替えて表示する。独立したメニュー項目・URL(旧`/admin/reports/monthly`)は無くなった): 通常の日次レポートと同じPV数・imp数・imp率・CL数・CL率・友だち追加数・友だち追加率・CV数・CVRを、月単位で合算して一覧表示する。`buildDailyReport()`が作る日次の行を`buildMonthlyReport()`で月ごとにグループ化・合算しているため、日次レポート側のPV数・imp数・CL数の値や「未入力は空欄のまま合算から除く」という扱いと必ず一致する
- **サマリ**(`/admin/reports/monthly-summary`): ポップアップ別・ポップアップ×シナリオ別・設置先×訴求×離脱地点×ポップアップ×シナリオ×中間別の3つの月次集計を、1ページに上から順に並べる。「表示する範囲」のラジオボタンで「期間合計」(開始月〜終了月の合算)か「特定の月」(1か月分)を選ぶ。内部では専用のAPI(`/api/report/monthly-summary`)を1回だけ呼び(友だち追加・成果・日次PV・流入経路/広告の設定は3つの集計で共通のため1回だけ読み込んで使い回し、Firestoreの読み取りを抑えている)、返された3つの集計の月ごとの行を名前ごとに`summarizeAdFunnelRows()`(`src/lib/ad-funnel-summary.ts`)で合算して表にする。縦に並べるのは、その範囲で稼働した(imp数・CL数・友だち追加・CVのいずれかが1以上。PV数は日次合計のフォールバックが入るため判定に使わない)ものだけ。各表にCSVダウンロードがある。3つの集計の内訳は次のとおり:
  - **ポップアップ別**: ポップアップ別日次レポートと同じ指標を、ポップアップごとに月単位で合算する(`buildPopupMonthlyReport()`)
  - **ポップアップ×シナリオ別**: 各流入経路に設定した「ポップアップ」「シナリオ」の組み合わせ(例: 「ポップアップA / シナリオ1」)ごとに、友だち追加時・成果発生時の流入経路(`sourceId`・`latestSourceId`)を流入経路管理の設定と突き合わせて、PV数・imp数・CL数・CL率・友だち追加数・友だち追加率・CV数・CVRを月単位で集計する(`getPopupScenarioLabelMap()`)。imp数・CL数は、データ取り込み時に「シナリオ」列の命名規則からポップアップ・シナリオを`extractPopupScenarioLabelFromScenarioName()`(`src/lib/scenario-popup.ts`)で取り出し、「ポップアップ / シナリオ」のラベルで日付ごとに合算して`daily_popup_scenario_ad_metrics`コレクション(ドキュメントID=`${日付}__${ラベルをencodeURIComponentしたもの}`)に保存し、同じラベルで紐付ける。PV数はこの単位の取り込み元が無いため、日次レポートの合計PV数をそのまま使う(組み合わせごとの実数ではない)。集計は設置先×訴求×…別と同様、ポップアップ別月次の`buildPopupDailyReport()`→`buildPopupMonthlyReport()`を流用している。「現在稼働中」の判定には、友だち追加・成果に加えてimp数・CL数の取り込みも含める(`getActivePopupScenarioLabels()`)。過去に取り込んだファイルは再度取り込む必要がある
  - **設置先×訴求×離脱地点×ポップアップ×シナリオ×中間別**: 流入経路の全要素の組み合わせ(=流入経路そのもの単位)で、PV数・imp数・CL数・CL率・友だち追加数・友だち追加率・CV数・CVRを月単位で集計する。この単位は流入経路(`sources`コレクション)の1件1件と同じであるため、ラベルには流入経路の自動生成名(`sources.name`、`src/lib/source-name.ts`の`buildSourceName()`で生成されたフルネーム)をそのまま使っている(`getSourceNameLabelMap()`)。imp数・CL数は、データ取り込み時に「シナリオ」列(命名規則付きの名前)の6要素(設置先・訴求・ポップアップ・シナリオ・離脱地点・中間)を`extractSourceNameFromScenarioName()`(`src/lib/scenario-popup.ts`)で取り出し、`buildSourceName()`と同じ「_」区切りで結合した名前を日付ごとに合算して`daily_source_ad_metrics`コレクション(ドキュメントID=`${日付}__${流入経路の名前をencodeURIComponentしたもの}`)に保存しておき、`sources.name`との完全一致で紐付けている(「その他」を設定した流入経路は名前が一致しないため紐付かない)。PV数はこの単位の取り込み元が無いため、ポップアップ別等と同様に日次レポートの合計PV数をそのまま使う(組み合わせごとの実数ではない)。集計はポップアップ別月次レポートと同じ`buildPopupDailyReport()`→`buildPopupMonthlyReport()`を、ポップアップ名の代わりに流入経路の名前をラベルとして流用している(`src/app/api/report/monthly-summary/route.ts`)。「現在稼働中」の判定には、友だち追加・成果に加えてこのimp数・CL数の取り込みも含める(`getActiveSourceLabels()`)。過去に取り込んだファイルはこの保存先に入っていないため、反映したい期間のファイルを再度取り込む必要がある
- 旧「ポップアップ別月次レポート」「ポップアップ×シナリオ別月次レポート」「設置先×訴求×…別月次レポート」の3画面は、この月次サマリに統合した(画面・メニュー・閲覧権限の選択肢は廃止。APIは月次サマリが使うため残している)

### データ取り込み

「データ取り込み」画面(`/admin/reports/ad-metrics-import`)は、Flipdesk等・PV数集計ツールからエクスポートしたCSVファイルの取り込み専用画面。以前は「日次レポート」「ポップアップ別日次レポート」「シナリオ別日次レポート」「離脱地点別日次レポート」「訴求別日次レポート」の各画面にそれぞれ取り込み口があったが、同じファイルを複数箇所で取り込み直す必要がありUI的にも分かりにくかったため、この画面に一本化している。画面は「フリップデスクデータ」(imp数・CL数、Flipdesk等のエクスポート用)・「PV数」(通常の日次レポート向けPV数、PV数集計ツールのエクスポート用)・「訴求別PV数」(訴求別日次レポート向けの訴求ごとのPV数)の3つのセクションに分かれており、それぞれ別ファイルとして取り込む。

**フリップデスクデータ**: 1回の取り込みで、通常の「日次レポート」(日付単位の合計)・「ポップアップ別日次レポート」(日付×ポップアップ単位の合計)・「シナリオ別日次レポート」(日付×シナリオ単位の合計)・「離脱地点別日次レポート」(日付×離脱地点単位の合計)・「訴求別日次レポート」(日付×訴求単位の合計)の5つにまとめて反映される。

- 取り込むファイルは「日付・自動ポップアップ表示回数・ポップアップ内のクリック数」等の列を持つ、シナリオ・日付ごとの行の一覧(Flipdeskのレポートエクスポートをそのまま利用できる)。見出し行から列の位置を自動判定するため、列の並び順が変わっても問題ない
- CSV(.csv)ファイルをそのままアップロードできる(文字コードはUTF-8・Shift_JISのどちらも自動判定。Excelファイル(.xlsx/.xls)は取り込めないため、CSVで保存し直す)
- 「日付」列でグループ化し、「自動ポップアップ表示回数」をimp数、「ポップアップ内のクリック数」をCL数として、同じ日付の行をすべて合算したうえで、日次レポート(`daily_ad_metrics`コレクション、ドキュメントID=日付)に取り込む
- ファイルに「シナリオ」「グループ」の列も含まれている場合は、以下の命名規則(｜は全角パイプ)でポップアップ名・シナリオ名・離脱地点名・訴求名をそれぞれ判定し、「日付」×「ポップアップ」・「日付」×「シナリオ」・「日付」×「離脱地点」・「日付」×「訴求」ごとに合算したうえで、ポップアップ別日次レポート(`daily_popup_ad_metrics`コレクション、ドキュメントID=`${日付}__${ポップアップ名をencodeURIComponentしたもの}`)・シナリオ別日次レポート(`daily_scenario_ad_metrics`コレクション、ドキュメントID=`${日付}__${シナリオ名をencodeURIComponentしたもの}`)・離脱地点別日次レポート(`daily_exit_point_ad_metrics`コレクション、ドキュメントID=`${日付}__${離脱地点名をencodeURIComponentしたもの}`)・訴求別日次レポート(`daily_appeal_ad_metrics`コレクション、ドキュメントID=`${日付}__${訴求名をencodeURIComponentしたもの}`)にも取り込む:
  `【クライアント名｜案件名】設置先｜訴求｜ポップアップA/ポップアップB｜シナリオA/シナリオB｜離脱地点｜中間｜`
  - 「グループ」列には`A`・`B`・`-`のいずれかが入る。ポップアップ・シナリオの項目が`ポップアップA/ポップアップB`のように`/`区切りでA/B2つ書かれている場合は、グループ列が`A`ならA側、`B`ならB側の値をポップアップ名・シナリオ名として使う。離脱地点・訴求は命名規則上A/Bの出し分けが無い前提のため、常に単一の値をそのまま使う(仮に`/`区切りで書かれていた場合は、ポップアップ・シナリオと同じロジックでグループ列に応じて選ぶ)
  - いずれの項目も`/`を含まない単一の値だけの場合は、グループ列の値に関わらずその値をそのまま名前として使う(判定ロジックは`src/lib/scenario-popup.ts`の`extractAppealFromScenarioName()`・`extractPopupFromScenarioName()`・`extractScenarioFromScenarioName()`・`extractExitPointFromScenarioName()`。それぞれ命名規則の2・3・4・5項目めを見ているだけで、4つは独立して判定される)
  - 「シナリオ」列の値が命名規則に合わない、日付が読み取れない等で名前を判定できなかった行は(ポップアップ・シナリオ・離脱地点・訴求それぞれ別々に)スキップされ、取り込み後にスキップ件数が表示される
  - 「シナリオ」「グループ」の列が見出しに見つからないファイルの場合は、日次レポート側の日付単位の合計のみが更新され、ポップアップ別・シナリオ別・離脱地点別・訴求別の取り込みはスキップされる(エラーにはならない)
- 同じ期間・同じ(日付, ポップアップ)・同じ(日付, シナリオ)・同じ(日付, 離脱地点)・同じ(日付, 訴求)を再度取り込んだ場合、値は合算されず最新の内容にそのまま置き換わる(Flipdesk側のエクスポートが指定期間をフルに含む形式のため)
- 取り込み・合算ロジックは`src/lib/ad-metrics-import.ts`の`parseAdMetricsRows()`に共通化されている

**PV数**: 「日付」「合計」の2列を持つファイル(見出し行から列の位置を自動判定)を取り込み、「合計」列の値をその日のPV数として日次レポート(`daily_ad_metrics`コレクション)に反映する。同じ日付を再度取り込んだ場合、値は合算されず最新の内容にそのまま置き換わる。imp数・CL数側とは別のファイル・別の取り込みボタンだが、書き込み先は同じ`daily_ad_metrics`コレクションで、Firestore側は`merge: true`で更新するため、どちらを先に取り込んでももう片方の値は消えない。取り込み・集計ロジックは`src/lib/pv-import.ts`の`parsePvRows()`。取り込んだPV数は、通常の日次レポート(`/admin/reports/daily`)の一覧に反映される(imp率(imp数 ÷ PV数)の計算にも使われる)ほか、ポップアップ別・シナリオ別・離脱地点別レポート側で個別のPV数が未入力の(日付, ポップアップ/シナリオ/離脱地点)についても、この日次合計PV数がそのまま表示に使われる(訴求別レポートはフォールバック対象外)

**訴求別PV数**: 訴求別日次レポート向けに、訴求ごとのPV数をまとめて取り込む。上記のPV数取り込みとは異なり「横持ち」形式のファイルを想定しており、見出し行に「日付」列と、訴求ごとに1列(その列の見出しセル自体に具体的な訴求名を入れたもの。例: 「日付」「スキンケア訴求」「美容訴求」...)が必要。各セルにはその日・その訴求のPV数を入力し、空欄のセルはその訴求のPV数が未計測として取り込み対象から除かれる。取り込み先は訴求別日次レポートと同じ`daily_appeal_ad_metrics`コレクション(ドキュメントID=`${日付}__${訴求名をencodeURIComponentしたもの}`)の`pvCount`フィールドで、既存のimp数・CL数のフィールドは変更しない(`merge: true`)。同じ(日付, 訴求)を再度取り込んだ場合、値は合算されず最新の内容に置き換わる。取り込み・解析ロジックは`src/lib/pv-import.ts`の`parseAppealPvRows()`、書き込みはimp数・CL数と同じ`/api/report/ad-metrics-by-appeal/import`のPOSTを共用している(bodyの`pvCount`が任意項目として追加されている)

### マニュアルページ

各ページの右上の「このページのマニュアル」ボタンは、表示中のページに対応するマニュアルのページを新しいタブで開く(対応表は`src/lib/admin-pages.ts`の`MANUAL_PAGE_MAP`。マニュアルのページを追加・変更したら、ここも更新すること。対応表にないページは、マニュアルの目次を開く)。サイドメニューの「マニュアル」は、管理画面内のページではなく、別URL(`https://lisma.jp/project/tool/manual`、`src/lib/admin-pages.ts`の`MANUAL_URL`)のマニュアルサイトを新しいタブで開く(`/admin/manual`にアクセスした場合も同じURLへ転送する)。マニュアルの内容は`src/app/admin/manual/content.ts`のデータ(画面ごとに概要・使い方・補足)で、プロジェクトのフォルダで`node scripts/build-manual-site.js`を実行すると、`manual-site/`に全体の目次ページ(`index.html`)、親メニューごとのフォルダ(`<グループID>/index.html`と、小項目ごとの`<グループID>/<項目ID>.html`)、`style.css`、全ページ共通のサイドメニュー`menu.js`が生成される(メニューは各ページに埋め込まず`menu.js`が描画する)。手書きでページを編集する場合は、機能ごとに`<h2>機能名</h2>`→説明・手順(`<ol>`)・小見出し(`<h3>`)の順に並べ、補足は`<h2 class="note-title">補足・注意点</h2>`+`<ul class="notes">`と書くと、オレンジの注意書きボックスで表示される(エラー・システムログのように1項目ずつ「意味」「解決方法」を並べたい場合は、`<div class="log-item">`の中に`<div class="log-head"><code class="log-stage">ステージ名</code><span class="log-level log-level-error">error</span></div>`と`<dl class="log-body"><dt>意味</dt><dd>…</dd><dt>解決方法</dt><dd>…</dd></dl>`を入れるカード形式を使う。レベルは`log-level-error`/`log-level-warn`/`log-level-info`)(アイコンは既定で三角の警告マーク。`<h2 class="note-title icon-exclaim">`にすると、オレンジの丸に「!」のアイコンになる)(表は`<li>`の中に`<table>`を入れてよい)(管理画面へのリンクは出さない。`--out`で出力先を変更できる)。リンクはすべて相対パスのため、フォルダごとWebサーバーにアップロードすればよい。画面の仕様を変更したら`content.ts`を更新し、再実行してアップロードし直すこと。
サイドメニューの構成は、友だち一覧・流入経路管理・広告管理・「ログ集計」(流入経路ログ・広告クリックログ・広告成果ログ・エラー・システムログ)・「レポート集計」(サマリ・日次・月次レポート・ポップアップ別・離脱地点別・訴求別・シナリオ別)・「データ」(データ取り込み・編集用成果ログ)・マニュアル、の順。サイドメニューには`src/lib/admin-pages.ts`の`ADMIN_NAV_ITEMS`で登録しており、レポート閲覧権限の選択肢(`REPORT_VIEWER_SELECTABLE_PAGES`)には含めていないため、管理者権限のユーザーにのみ表示される。

### 成果単価と請求額

- `/admin/purchase-links`(広告管理)で、広告ごとに「成果単価」(円、0以上。`PurchaseLinkDoc.unitPrice`)を入力できる(新規登録・編集欄・一覧の「成果単価」列。未設定は0円扱い)。
- 各レポートの「請求額」は、**成果(非表示を除く)ごとにその広告の成果単価を合算**した金額。`getEffectiveCvEntries()`(`src/lib/report-cv.ts`)が、成果ごとに`billingAmount`(単価)を付け(自動計測の成果は`purchaseLinkId`、CSV等で手動追加した成果は広告名の完全一致で`purchase_links`と突き合わせる。一致しない・単価未設定は0)、各集計関数(日次・ポップアップ別・シナリオ別・離脱地点別・訴求別・月次)がCV数と同じ単位(日付×ポップアップ等)で合算している。月次・サマリでは`summarizeAdFunnelRows()`の`billing`で合算する。
- 請求額が出る画面: 日次・月次レポート(日次・月次とも)、ポップアップ別・離脱地点別・訴求別・シナリオ別、サマリ(3つの表)。各画面のCSVにも「請求額(円)」の列を出力する。
- 単価は成果が発生した時点の値を保存せず、集計時点の広告の現在の単価を使う。単価を変更すると過去分の請求額も新しい単価で再計算される。

### 管理画面ログイン・ユーザー権限

管理画面(`/admin/**`)は、ID・パスワードでのログインが必須。未ログインの場合は`/login`へリダイレクトされる。

- **アカウント管理**: ログインアカウントは`admin_users`コレクションに保存され、`/admin/users`画面(管理者権限のみ閲覧可)から作成・編集・削除できる。最初の1人目は画面からは作れない(ログインできる人が誰もいないため)ので、`scripts/create-admin-user.js`で直接作成する(「事前準備」参照)
- **権限(ロール)は2種類**:
  - **管理者権限**: 全ページの閲覧・編集が可能(ユーザー管理画面も含む)
  - **レポート閲覧権限**: ユーザーごとに指定したページのみ「閲覧」できる(編集は一切不可)。`admin_users`ドキュメントの`allowedPages`配列。ユーザー作成・編集画面でページ単位のチェックボックスから指定する。選択肢は「日次・月次レポート」(合算。同じページ内で日次/月次を切り替える)、日次4レポート(「ポップアップ別日次レポート」「離脱地点別日次レポート」「訴求別日次レポート」「シナリオ別日次レポート」)と「月次サマリ」の6レポートに加え、「広告クリックログ」「広告成果ログ」の合計8つのみ(`src/lib/admin-pages.ts`の`REPORT_VIEWER_SELECTABLE_PAGES`)で、友だち一覧・流入経路管理・その他のログ・データ取り込み等は選択できない(APIでもこの8つ以外の値は無視される)。広告クリックログ・広告成果ログの閲覧用表示では「友だち名」の列とユーザー名の絞り込みを非表示にし、`/api/admin/table`もサーバー側で友だち名を返さない(IDは表示される)。マニュアルは閲覧用が`https://lisma.jp/project/tool/manual/user/`配下(管理者用と同じ構成)で、サイドメニュー・各ページ右上のリンクは権限に応じて切り替わる
- **パスワード**: `src/lib/password.ts`でNode.js標準の`crypto.scryptSync`によりハッシュ化して保存する(平文やbcrypt等の追加ライブラリは使用していない)。8文字以上を必須にしている
- **セッション**: ログインに成功すると、ユーザー情報(権限・閲覧可能ページを含む)を署名付きで埋め込んだトークンを`httpOnly`のCookie(`admin_session`、有効期限30日)として発行する。署名にはWeb Crypto API(`crypto.subtle`のHMAC-SHA256)を使っており、Node.js実行環境のAPI RouteからもEdge Runtime(後述のMiddleware)からも検証できるようにしている。署名鍵が`ADMIN_SESSION_SECRET`
- **アクセス制御の仕組み**: `src/proxy.ts`が`/admin/**`・`/api/admin/**`・`/api/report/**`・`/api/sources/**`・`/api/purchase-links/**`・`/api/logs/export-to-sheet`へのリクエストを検証する。未ログインならログイン画面へリダイレクト(APIの場合は401)、レポート閲覧権限で許可されていないページへアクセスした場合は`/admin/no-access`へリダイレクトする。ただし、ログイン直後の遷移先である`/admin`(友だち一覧)はレポート閲覧権限では閲覧できないページのため、そこに来た場合に限り「権限がありません」と表示する代わりに、閲覧できるページの先頭(`allowedPages[0]`)へ自動的に連れて行く。LINE Webhook(`/api/line/webhook`)・計測用エンドポイント(`/api/track/click`・`/api/track/conversion`)・LIFFの友だち追加(`/liff/add`)・クライアントエラー報告(`/api/logs/client`)は、LINE・LP・LIFF側から直接(ログインしていない状態で)呼ばれるため、認証対象から除外している
- **レポート閲覧権限は編集不可**: 上記のミドルウェアで、レポート閲覧権限のユーザーからの`/api/admin/**`・`/api/report/**`・`/api/sources/**`・`/api/purchase-links/**`へのGET以外のリクエスト(PV数・imp数・CL数の編集、CSVインポート等)は403で拒否する(閲覧のみのPOST `/api/admin/table`は例外で、ルート側で許可ページを検証する)。あわせて各日次レポート画面側でも、`src/app/admin/CurrentUserContext.tsx`経由でログインユーザーの権限を受け取り、レポート閲覧権限の場合は「編集」ボタン自体を表示しない(見た目の制御。実際の編集禁止はミドルウェア側で強制している)
- **権限変更の反映タイミングに関する注意**: 閲覧可能ページの一覧はログイン時にセッションCookieへ埋め込まれるため、ユーザー管理画面で権限(ロール・閲覧可能ページ)を変更しても、そのユーザーがすでにログイン中の場合は反映されない。変更後は一度ログアウト・再ログインしてもらう必要がある
- なお、この仕組みは管理画面の「ページ単位」のアクセス制御であり、各ページが参照するFirestoreのセキュリティルール自体は別途の設定が必要な点に注意(本ツールはFirebase Admin SDK経由のサーバーサイド読み書きが中心のため、現状は未設定でも支障はない想定)

### テスト用データの投入(開発・画面確認用)

`scripts/seed-test-data.js` を使うと、「友だち一覧」「流入経路ログ」「広告ログ(クリックログ・成果ログ)」の画面確認用に、ファネル風の比率(件数100件の場合: 流入経路クリック約130件(離脱分込み) → 友だち追加100件 → 広告クリック約50件 → そのうち約30件が成果)でテストデータをまとめて投入できる。

**前提**: `/admin/sources`・`/admin/purchase-links` にあらかじめ1件以上、流入経路・広告を登録しておくこと(投入するテストの友だち・クリック・成果は、そこに登録済みのものからランダムに割り振られる)。

```bash
node scripts/seed-test-data.js        # 100件(既定)投入する
node scripts/seed-test-data.js 50     # 件数を指定して投入する(例: 50件)
node scripts/seed-test-data.js --undo # このスクリプトで投入したテストデータをすべて削除する
node scripts/seed-test-data.js --from 2026-10-01 --to 2026-10-09 --dry-run  # 期間指定: 件数だけ確認(書き込まない)
node scripts/seed-test-data.js --from 2026-10-01 --to 2026-10-09             # 期間指定: 実際に投入(プロジェクトID入力で確認)
```

期間指定(`--from` / `--to`、日本時間)では、管理画面に登録済みの流入経路・購入リンクを使い、1日ごとに友だち追加・流入経路クリック・購入リンククリック・成果を作る。1日あたりの件数は既定で友だち追加15〜25人・CV 5〜10件で、`--friends-per-day 10-20` `--cv-per-day 3-6` で変更できる。現在時刻より未来の日時は作らない。投入データのIDは `test_` で始まるため、`--undo` で削除できる。友だちには本番と同じ仕組みでID(追加日時が古い順の連番)も採番する。IDなしで投入済みのデータには、`node scripts/assign-friend-ids.js --yes` で後から付与できる(`--yes` なしだと件数の確認のみ)。

- `.env.local`の`FB_PROJECT_ID`/`FB_CLIENT_EMAIL`/`FB_PRIVATE_KEY`を使って、実際に設定されているFirestoreに直接書き込む(本番と同じFirebaseプロジェクトを指している場合は、そこに書き込まれる点に注意)
- 投入されるテストデータは`friends`・`clicks`(`linkType: "add_friend"`の流入経路クリックと`linkType: "purchase"`の広告クリックの両方を含む)・`conversions`の3コレクション。すべてのuserId/clickId/conversionIdが`test_`から始まるIDになっているため、`--undo`で本物のデータを巻き込まずに安全に削除できる
- 友だちごとに、その友だち追加の直前に流入経路リンクをクリックしたログを必ず1件作成するほか、友だち追加に至らなかった(離脱した)流入経路クリックも、友だち数の約30%追加で作成する(`userId`なしのクリックとして記録される)
- 友だちの流入経路(`sourceId`)・広告(`purchaseLinkId`)は、登録済みのものから均等にランダムで割り振られる。友だち追加日時は直近30日間でランダムに分散される
- 「友だち一覧」の状態列のテスト用に、約8%の友だちは「ブロック/解除済み」状態(`unfollowedAt`あり)として作成される

### 友だちデータ・ログ・レポートの全削除

`scripts/delete-all-logs.js`を使うと、テスト・確認用に投入したデータを一掃できる(本番環境への反映機能ではなく、画面をまっさらな状態に戻すためのローカル実行用スクリプト)。削除対象は以下のコレクション:

- `friends`(友だち一覧)
- `clicks`(クリックログ。流入経路ログ・広告ログの両方を含む)
- `conversions`(成果ログ、自動計測分)
- `report_cv_entries`(編集用成果ログ画面での手動追加・非表示設定)
- `event_logs`(エラー・システムログ)
- `daily_ad_metrics`・`daily_popup_ad_metrics`・`daily_scenario_ad_metrics`・`daily_exit_point_ad_metrics`・`daily_appeal_ad_metrics`(各レポートのimp数・CL数・PV数)
- `daily_source_ad_metrics`・`daily_popup_scenario_ad_metrics`(月次サマリ用のimp数・CL数)
- 日次レポートのメモは`daily_ad_metrics`の一部のため、一緒に削除される

標準では、流入経路管理・広告管理に登録したマスタ(`sources`・`purchase_links`)は削除しない。`--all`を付けると、`sources`・`purchase_links`・`counters`(友だちIDの連番。削除すると連番が1から振り直される)も削除してテスト環境を完全に初期化する。管理画面のログインアカウント(`admin_users`)はどちらの場合も削除しない。

```bash
node scripts/delete-all-logs.js        # 削除せず、各コレクションの件数だけ確認する
node scripts/delete-all-logs.js --yes  # 実際に削除する(元に戻せません)
node scripts/delete-all-logs.js --all --yes  # 流入経路・広告・カウンタも含めてすべて削除する
node scripts/delete-all-logs.js --logs-only --yes  # ログ(クリック・成果・エラー)だけを削除する(友だち・レポートの取り込みデータ・流入経路・広告は残す)
```

`--yes`を付けて実行すると、削除前に対象のFirebaseプロジェクトIDの入力を求められる(違うプロジェクトを指していないかの最終確認)。本番のFirebaseプロジェクトに接続している場合、`--yes`を付けると本番データが完全に削除される。実行前に`.env.local`の`FB_PROJECT_ID`が意図したプロジェクトを指しているか必ず確認すること。

## ログインできない場合・初回セットアップ

ログイン画面(`/login`)から、次の2つの画面に進める。どちらも、サーバーの環境変数`ADMIN_SETUP_KEY`(セットアップキー)を知っている人だけが実行できる。

- **初めてログインする方はこちら**(`/login/setup`): 管理者アカウントが1つも無いときだけ、最初の管理者アカウント(ログインID・表示名・パスワード)を作成する。管理者アカウントがすでにある場合は、キーが正しくても作成できない(トランザクションで二重作成も防いでいる)。2人目以降は「ユーザー管理」から作成する。
- **ID・パスワードを忘れた方はこちら**(`/login/recover`): セットアップキーを入力すると登録済みアカウントのログインID・表示名・権限の一覧が表示され、アカウントを選んで新しいパスワードを設定できる。

セキュリティ上の仕組み:

- `ADMIN_SETUP_KEY`が未設定、または16文字未満の場合は、この2つの機能全体を無効にする(画面にも設定が必要な旨を表示)。使わない時は空にしておくのが最も安全。
- キーの照合は定数時間比較。5回連続で間違えると15分間ロックする(失敗回数・ロック状態はFirestoreの`auth_throttle`コレクションの`setup_key`ドキュメントに保存。全体で1つのため、複数のIPから試されても総当たりできない)。
- 初回セットアップ・パスワード再設定・アカウント一覧の表示は、「エラー・システムログ」に`auth.initial_setup`・`auth.password_reset`・`auth.recover_list`として記録される(誰が操作したかではなく、操作があったことの記録)。
- 関連するAPI: `GET /api/auth/setup-status`(キーの設定有無と管理者の有無のみ返す)、`POST /api/auth/setup`、`POST /api/auth/recover`(`action: "list"`/`"reset"`)。いずれもログイン前に呼ぶため、ミドルウェアの認証対象外。

`scripts/create-admin-user.js`によるコマンドラインでの作成・パスワード上書きも、引き続き使える(サーバーの認証情報を持っている人の最後の手段)。

## データ取得の設計(Firestoreの読み取りを抑える工夫)

- **流入経路(`sources`)・広告(`purchase_links`)のメモリキャッシュ**(`src/lib/settings-cache.ts`): 件数の少ない設定用コレクションで、レポートのたびに全件が必要になるため、サーバーのメモリに最大60秒保持する。流入経路・広告の登録/編集/削除APIでキャッシュを破棄するので、同じサーバー内では編集直後から最新の内容で集計される(サーバーが複数台に分かれる環境では、遅くとも60秒後に反映)。
- **一覧を返すGETのAPIは常に最新を返す**: 流入経路・広告・ユーザーの一覧APIは、リクエストを読まないGETのため、何も指定しないとNext.jsがビルド時の結果を使い回す(本番で登録内容が一覧に出なくなる)。そのため`export const dynamic = "force-dynamic"`を付けている。同種のGETのAPIを追加するときも付けること。
- **月次サマリは1回の問い合わせ**: 3つの集計で共通のデータ(友だち追加・成果・日次PV)を1回だけ読み込んで使い回す。
- **日次・月次の切り替え**: 一度開いた画面は残したまま表示を切り替えるので、切り替えのたびに再取得しない(「表示」を押したときだけ取得する)。
- 友だち追加・成果・imp/CL等は日付範囲で絞り込んで読み込む。範囲を広げるほど読み取りが増えるため、必要な期間だけ指定する。
