# 運用コストの整理

想定ボリューム(1日あたり):友だち追加 100件 / CV 30件 / 購入リンククリック 200件 / 流入経路リンククリック 100件

## 1. 費用が発生する要素

| 項目 | 何に使うか | 費用感 |
|---|---|---|
| Firebase Firestore | 友だち・クリック・CVデータの保存 | 従量課金(下記で試算) |
| ホスティング(Vercel) | アプリ自体の稼働 | Hobby(無料)は商用利用不可のため、事業用途では Pro:**$20/シート/月〜** |
| LINE Messaging API | Webhook受信・プロフィール取得 | このツール自体はメッセージ送信をしないため追加費用なし(Lステップの既存契約とは別) |
| ドメイン・SSL | 本番URL | ドメイン代 年間1,000〜2,000円程度(SSLはVercel/Let's Encryptで無料) |
| Googleスプレッドシート連携(GAS) | CSVのスプレッドシート送信 | 無料 |

## 2. Firestoreの費用試算

無料枠(Sparkプラン):1日あたり **読み取り5万件・書き込み2万件・削除2万件**、ストレージ1GiB、通信10GiB/月まで無料。
超過分はBlazeプラン従量課金(Iowaリージョン基準):

- 読み取り $0.03 / 10万件
- 書き込み $0.09 / 10万件
- 削除 $0.01 / 10万件
- ストレージ $0.0002 / GiB / 月

**通常のイベント処理(クリック記録・友だち追加・CV記録)** だけで見ると:

- 書き込み:クリック300件 + 友だち追加100件 + CV 30件 + 再クリック補正分 ≈ 1日450〜500件程度(月1.5万件弱)
- 読み取り:友だち検索・重複チェック等 ≈ 1日300〜400件程度(月1万件程度)

→ どちらも無料枠に対して余裕があり、この部分だけなら実質無料で運用できる。

導入前から友だちだった人の自動登録(流入経路リンクの初回クリック時)は、未登録のユーザーが1回リンクを押すごとに、LINEのプロフィール取得(外部API。Firestoreの読み取りではない)と、友だち・連番カウンタの読み書きが数件発生する程度。1人につき一度きりで、導入前の友だちの人数分だけ(例: 1万人なら書き込み数万件。1日の無料枠(2万件)を超えそうな場合は、数日に分かれて登録されるため通常は問題にならない)。流入経路の一括登録・友だち情報の一括更新(CSV)も、対象の件数分の書き込みが発生する(いずれも1回の上限あり)。

## 3. ✅ 対応済み:ログ画面の全件読み込みを解消

以前は、クリックログ・流入経路ログ・CVログ・友だち一覧の各画面を開くたびに、友だちデータ全件(CVログ画面ではクリックデータ全件、友だち一覧ではCVデータ全件も)をFirestoreから読み込む実装になっていた。データが増えるほど読み取り件数が線形に増え続け、将来的にコストと表示速度の両方が悪化していく懸念があった。

| 経過期間 | 友だち累計 | クリック累計 | (対応前)クリックログ表示1回の読み取り | (対応前)CVログ表示1回の読み取り |
|---|---|---|---|---|
| 1ヶ月後 | 約3,000件 | 約9,000件 | 約3,000件 | 約12,000件 |
| 6ヶ月後 | 約18,000件 | 約54,000件 | 約18,000件 | 約72,000件 |
| 1年後 | 約36,500件 | 約109,500件 | 約36,500件 | 約146,000件 |

**実施した対策**:各ログ画面(クリックログ・流入経路ログ・CVログ・編集用成果ログ・友だち一覧)を、コレクション全体を読み込む方式から「画面に表示している行に登場する友だち・クリック・CVだけ」をピンポイントで取得する方式に変更した。

- 友だち一覧・各ログ:50件ずつのカーソル式ページネーション。次のページを開いたときに続きの50件だけを読み込む(全件は読み込まない)。ログ系は開いた時点では当日分のみ(日時の範囲指定で読み込み)
- 表示した行に登場する `userId` / `clickId` だけをまとめて取得(`getAll`)
- 友だち一覧の購入回数集計:表示中の50人の `userId` だけを対象に `conversions` を検索(`where(..., "in", ...)` を10件ずつのチャンクに分けて問い合わせ)
- ユーザー名・流入経路などで絞り込む場合は、一定件数(200件)ずつ読み込んで条件に合う行を拾う。1回の操作で読み込む件数の上限は1,000件

- レポート系:日ごとの集計(`daily_stats`。1日につき1ドキュメント)を読む。期間30日で約30件、1年でも約365件。結果は2分間キャッシュ

これにより、データがどれだけ増えても1画面あたりの読み取り件数は「1ページ分(50件程度。絞り込み時は最大1,000件)」で頭打ちになり、コストも表示速度もこの先ずっと安定する。友だち・クリック・CVがどれだけ蓄積されても、上記の表のような右肩上がりの読み取り増加は発生しない。

## 4. まとめ

- 今の想定ボリューム(月間)であれば、Firestore単体の費用はほぼ0円に収まる
- 事業として運用する場合、ホスティングをVercel Proにするなら **$20/シート/月〜**(無料のHobbyは商用利用不可のため)
- ドメイン代が年1,000〜2,000円程度
- ログ画面の読み込み方式の見直しは対応済み(3章のとおり、サーバー側ページネーションで1画面あたりの読み取りは1ページ分に頭打ち。レポートも日次集計・キャッシュで読み取りを削減済み)。データが増えても費用・表示速度は悪化しにくい

## 5. Vercelの課金体系(シート制)

- Vercelの料金は「チーム(アカウント)の利用人数(シート)」に対してかかる。**プロジェクト数には課金されない**
  - Hobby(無料):プロジェクトは200個まで作成可能。ただし商用利用不可
  - Pro:**$20/シート/月**($20分のクレジット込み)。プロジェクト数は無制限
- 「複数人での管理が可能」という記載は、1つのProチームに複数人を招待でき、その人数分だけ $20×人数 の請求になるという意味で、プロジェクト数とは無関係
  - チームに1人だけなら $20/月
  - チームに3人招待すれば $20×3 = $60/月
  - そのチーム内でプロジェクトを1個作ろうが100個作ろうが、基本料金部分は変わらない
- プロジェクト横断で利用量(帯域・関数実行回数・ビルド時間など)が合算され、含まれる無料枠を超えた分だけ従量課金される

## 6. 案件(クライアント)ごとにツールを展開する場合の構成

**Vercel側**:同じアカウント内に、案件ごとに別々のVercelプロジェクトを作成する。

- 案件ごとにリポジトリをフォーク(または同じリポジトリを元に)して、Vercel上で新しいプロジェクトとしてインポート
- 各プロジェクトごとに個別の環境変数(`.env.local`相当)を設定し、接続先(Firebase・LINEチャネル)を切り替える
- Vercel側の固定費は追加されない(1アカウント内で完結)

**Firebase側**:案件ごとに新しいFirebaseプロジェクトを作成し、そのプロジェクトの

- `FB_PROJECT_ID` / `FB_CLIENT_EMAIL` / `FB_PRIVATE_KEY`(サービスアカウントキー)

を、対応するVercelプロジェクトの環境変数に設定する。案件ごとに無料枠(読み取り5万件/日など)が新たに使えるため、案件を分けるほうがコスト管理・容量管理がしやすい。

**あわせて必要になるもの**:LINE公式アカウント自体も案件ごとに別物なので、

- LINE Developersの Messaging APIチャネル(Webhook URL・チャネルアクセストークン)
- 友だち追加用LIFFアプリ
- 購入リンクごとのLIFFアプリ

も個別に用意し、それぞれのVercelプロジェクトの環境変数に紐づける。

**注意点**:Firebaseプロジェクトが増えるほど、サービスアカウントキーやAPIキーの管理(どの案件がどのキーか)が煩雑になりやすいので、命名規則や管理表を用意しておくと安心。
